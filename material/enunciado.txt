2. Contexto del caso
Suministros Andinos SAS (empresa ficticia) vende papelería, tecnología y mobiliario de oficina
a empresas. Sus clientes envían solicitudes en texto libre por correo, formularios y mensajería.
Hoy una persona lee cada mensaje, decide si es un pedido, una consulta o una queja, digita los
datos en una hoja de cálculo y avisa al área encargada. El proceso es lento, tiene errores de
digitación y las quejas urgentes se pierden.
Tu tarea es construir un prototipo que automatice este proceso usando IA, una API propia y una
base de datos SQL.

Ejercicio 1 Flujo de automatización con IA 30 pts
Construye un flujo en n8n, Make, Power Automate o Zapier (el que prefieras) que procese
automáticamente las solicitudes entrantes.
Requisitos
1. Disparador: el flujo recibe la solicitud por webhook o formulario con este formato:
POST /webhook/solicitud
{
"cliente_email": "compras@ferreteriaeltornillo.com",
"mensaje": "Buenos días, necesitamos 10 resmas de papel carta para el viernes, es urgente."
}
2. Clasificación y extracción con LLM: envía el mensaje a un modelo de lenguaje que
devuelva únicamente un JSON válido con esta estructura:
{
"tipo": "pedido | consulta | queja",
"producto": "nombre del producto mencionado o null",
"cantidad": 10, // número o null
"urgencia": "baja | media | alta",
"resumen": "frase corta que resuma la solicitud"
}
3. Validación: si el LLM devuelve un JSON inválido o incompleto, el flujo debe reintentar una vez.
Si vuelve a fallar, guarda la solicitud marcada para revisión manual. El flujo nunca debe
detenerse con un error sin control.
4. Asociación con la base de datos: el flujo debe relacionar el correo con un cliente existente
y el nombre del producto con un producto del catálogo, usando la API del Ejercicio 2. Ten en

Ejercicio 2 API REST en Python 25 pts
Construye una API con FastAPI o Flask conectada a la base de datos del archivo
datos_prueba.sql (SQLite o PostgreSQL).
Endpoints requeridos
Método Ruta Descripción
GET /clientes?email= Busca un cliente por correo. Responde 404 si no existe.
GET /productos?q= Busca productos por nombre (búsqueda parcial, sin distinguir
mayúsculas). Devuelve el stock de cada uno.
POST /solicitudes Crea una solicitud. Valida los campos obligatorios y los valores
permitidos de tipo y urgencia. El estado inicial es pendiente.
GET /solicitudes Lista solicitudes con filtros opcionales tipo, estado y urgencia, y
paginación con limit y offset.
GET /solicitudes/{id} Detalle de una solicitud, incluyendo el nombre del cliente y del
producto.
PATCH /solicitudes/{id} Cambia el estado. Al pasar a resuelta se debe registrar
automáticamente la fecha de resolución.
Reglas de negocio
(cid:127) Si la solicitud es un pedido y la cantidad supera el stock del producto, la respuesta de POST
/solicitudes debe incluir "sin_stock": true. La solicitud se guarda de todas formas.
(cid:127) Los errores deben devolver códigos HTTP correctos (400/422, 404, 500) con un mensaje claro
en JSON.
(cid:127) No se permite volver una solicitud resuelta a pendiente.

Ejercicio 3 Consultas SQL 15 pts
Sobre la base de datos de datos_prueba.sql, escribe las siguientes consultas en el archivo
/sql/consultas.sql. Cada consulta debe llevar un comentario que indique a qué punto
responde. Las consultas deben funcionar en el motor que elegiste.
1. Lista las solicitudes pendientes con el nombre del cliente, el nombre del producto, el tipo y la
urgencia, ordenadas de la más antigua a la más reciente.
2. Muestra la cantidad de solicitudes por tipo y el porcentaje que representa cada tipo sobre el
total, redondeado a un decimal.
3. Muestra los clientes que tienen 2 o más quejas, con su nombre, ciudad y número de quejas,
de mayor a menor.
4. Calcula el tiempo promedio de resolución en horas por tipo de solicitud, considerando
solo las solicitudes resueltas.
5. Lista los pedidos cuya cantidad supera el stock actual del producto, mostrando el cliente,
el producto, la cantidad pedida, el stock y el faltante.
6. Para cada cliente, muestra únicamente su solicitud más reciente (fecha, tipo y estado).
Usa una función de ventana o una subconsulta.
Nota: también se evalúa la legibilidad: formato, alias claros y uso correcto de JOIN. Si encuentras
alguna inconsistencia en los datos, menciónala en un comentario.

Anexo A. Modelo de datos
El archivo datos_prueba.sql crea las siguientes tablas y carga los datos de ejemplo:
clientes
Columna Tipo Descripción
id INTEGER (PK) Identificador
nombre VARCHAR(120) Razón social
ciudad VARCHAR(60) Ciudad
email VARCHAR(120) UNIQUE Correo de contacto
fecha_registro DATE Fecha de alta como cliente
productos
Columna Tipo Descripción
id INTEGER (PK) Identificador
nombre VARCHAR(120) Nombre del producto
categoria VARCHAR(60) Papelería, Tecnología, Mobiliario o Impresión
precio NUMERIC(12,2) Precio unitario en pesos colombianos
stock INTEGER Unidades disponibles
solicitudes
Columna Tipo Descripción
id INTEGER (PK) Identificador
cliente_id INTEGER (FK) Referencia a clientes.id
producto_id INTEGER (FK, nullable) Referencia a productos.id
tipo VARCHAR(20) pedido, consulta o queja
cantidad INTEGER (nullable) Solo aplica para pedidos
urgencia VARCHAR(10) baja, media o alta
estado VARCHAR(20) pendiente, en_proceso o resuelta
mensaje TEXT Texto original enviado por el cliente
fecha_creacion TIMESTAMP Fecha y hora de recepción
fecha_resolucion TIMESTAMP (nullable) Fecha y hora en que se resolvió
Puedes agregar columnas o tablas si tu solución lo necesita (por ejemplo, un campo
requiere_revision o el resumen generado por el LLM). Documenta los cambios en el README.
